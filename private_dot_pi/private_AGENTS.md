# Instructions for agents working in ~/.pi

## Scope

- Edit files in `~/.pi/` only. Do **not** edit `~/.local/share/chezmoi/` unless the user explicitly asks for that.
- After changes, suggest `chezmoi status` and `chezmoi add <path>` for files the user wants persisted.

## Commands

Run from `~/.pi` unless noted.

- Full test suite (CI parity): `sh agent/scripts/run-extension-tests.sh`
- One TypeScript test: `npx -y tsx --test <path>`
- Shell tests: `sh agent/scripts/tests/merge-settings.test.sh`
- Extension load check: `pi --no-session --no-extensions -e <ext-path> --no-tools -p "reply: ok"`
- Regenerate settings: `sh agent/scripts/merge-settings.sh`
- Catalog and Artificial Analysis CLI: `node agent/extensions/09-catalog/aa/cli.ts` (see `agent/extensions/09-catalog/README.md`)
- CI failures: `gh run list --repo guaje/dotfiles --limit 10`; `gh run view <run-id> --repo guaje/dotfiles --log-failed`

Before changing benchmark routing, published assets, or their maintenance workflow, read `agent/extensions/04-subagents/BENCHMARK-ROUTING.md`. Before changing tests, read `agent/extensions/TESTING.md`.

## Settings

- `agent/settings.config.json` is the editable source of truth. `agent/settings.json` is generated by `agent/scripts/merge-settings.sh`; never edit it directly.
- Enable extensions with normal paths like `"extensions/07-native-notify.ts"`. A leading `-` is this repo's disable/exclude marker in the merged-settings convention — do not use it to enable.
- Register every extension, including disabled ones, in `agent/settings.config.json`.
- CLI equivalents: `pi -e <source>` loads an extension explicitly; `pi --no-extensions` disables discovery.

## Portability

Avoid hardcoding absolute paths, version numbers, and model/provider IDs in scripts, tests, extensions, or generated files.

- Derive paths relative to the current file, repository root, `$HOME`, or documented config locations.
- Read models/providers from `agent/settings.config.json`, `agent/models.json`, health-cache output, or the model registry.
- Discover package versions from installed metadata or command output — never versioned cellar paths.
- If a literal identifier is unavoidable in a unit fixture, use synthetic names (for example `test-provider/test-model`).

## Runtime state

- `agent/subagent-outcomes.json` is a bounded local work log. Never add it to chezmoi or git.

## Theming

- Preferred theme: `agent/themes/catppuccin-mocha.json`. Keep UI colors, warnings, previews, and syntax styling consistent with it.
- Prefer existing theme tokens and output conventions over inventing styling. `01-permissions/` and `00-hud/` preserve Catppuccin-compatible semantic roles.

## Chezmoi and commits

`~/.pi/` is the editable working copy. `~/.local/share/chezmoi/` is its tracked source-of-truth repo.

- Do not mutate chezmoi source state unless the user asks. Preserve unrelated destination drift.
- Use `chezmoi source-path <target>` to confirm the mapping before suggesting commands; naming is not uniform.
- Suggest `chezmoi status`, then `chezmoi add <changed-file>` for intended files.
- When asked to commit in the chezmoi repo: review `git status` and diffs, stage only intended files with explicit `git add`, and use short imperative messages.

## GitHub workflow

Pi files tracked in chezmoi are validated by `~/.local/share/chezmoi/.github/workflows/pi-tests.yml`.

- If changing package scopes, test fixtures, model/provider assumptions, or skill invocation behavior, update local tests and that workflow together.
- Keep stub payloads inside the test that owns them. Do not add a PATH `pi` stub to the workflow without a consuming test.
