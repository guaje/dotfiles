# SSH Handoff

`/ssh` connects Pi tools and optional session authority to a selected SSH workspace. It discovers concrete aliases from `~/.ssh/config`, waits for explicit selection before `ssh -G`, and never enables agent forwarding or changes SSH host-key policy. Workspace selection opens a remote directory browser rooted at `$HOME`; it lists directories (including hidden ones), supports parent navigation and manual absolute paths, and validates the final directory remotely.

Commands: `/ssh`, `/ssh toggle`, `/ssh status`, `/ssh sync`, `/ssh pull`, and `/ssh disconnect`. The shortcut and remote root resolve nested-first from settings, with legacy flat-key fallback:

```json
"handoff": {
  "remoteRoot": "~/.local/state/pi/remote-sessions",
  "hotkey": "ctrl+alt+s"
}
```

The hotkey must be a documented Pi keybinding and cannot replace protected built-ins; invalid values safely use `ctrl+alt+s`. The resolved binding appears in `/hotkeys`. Custom `keybindings.json` remaps can still create runtime conflicts; Pi reports those conflicts and skips protected collisions. Sync uses protocol v3: one bounded JSON request and one response over SSH stdin, with no local fallback. The helper reports its snapshot and chunk caps during the `version` handshake and the client uses the smaller of the two, so the size rules are negotiated rather than duplicated. Payloads above `DIRECT_COMMIT_BYTES` upload as staged chunks (`begin-upload`/`put-chunk`/`finish-upload`) under the same lock and lease; the helper refuses a transfer whose declared total will not fit the remote filesystem, verifies every chunk hash plus the assembled hash, commits atomically under the same CAS as a single-shot commit, and never exposes or commits a partial transfer (abandoned staging is pruned, failures send `abort-upload`, and long uploads renew the lease). Only a genuine `generation or hash conflict` is reported as a conflict; any other remote rejection is reported as offline carrying the underlying reason, and oversized payloads are refused locally before any SSH round trip. Expired locks require explicit, state-checked recovery. The Handoff backend registry exposes only current remote-route availability to Permissions. When connected with tools routed remotely, Permissions may offer session-only YOLO; it bypasses only Permissions-owned Bash/write/edit checks for those routed remote operations. It never enables local tools, direct SSH, subagents, or Handoff connection/helper-install confirmations. Toggling local, disconnecting, route loss, and shutdown immediately revoke YOLO and do not restore it on reconnect.

`/ssh pull` makes the connection bidirectional: it downloads the committed remote snapshot (chunked, hash-verified) and reconciles it against this session's entry tree. Shared entry ids are the common lineage; each side's remainder is its own branch. Three outcomes, all reported: no divergence, the imported remote turns grafted as a sibling branch under the shared ancestor, or a refusal that changes nothing (unrelated lineages, an entry id reused with different content, or remote entries whose parent is missing). A merge never rewrites the session you are in: the merged document is a new file (imported turns first, then local entries, `parentSession` recorded in the header) and the original file stays on disk as the fallback. Because Pi adopts the last entry of a file as the current position, the landing spot is written into the file itself — handoff's bookkeeping entries are chained onto the chosen branch and end the file — so switching alone lands the session there, the choice survives reopening the file, and nothing has to write after the switch (the pre-switch context and `pi` are stale once a session is relocated). Entry ids are preserved, which makes repeated pulls no-ops, and an identical merged file already on disk is reused instead of duplicated. Resume still routes a remote session without hydrating it; only pull imports history, and it imports it beside your branch rather than over it. Attaching a foreign lineage triggers detection automatically: after `/ssh resume` (including the resume option of the connect flow) the remote snapshot is compared with this session and, when it diverges or is ahead, the user is told — `Remote session on <alias> diverges from local by N turns from checkpoint <id>; this session has M turns it does not.` or `... is N turns ahead of this session.` — and asked whether to retrieve those turns. Retrieving the turns and where to land are separate agreements: `Pull remote history?` then `Go to the pulled turns?` — yes ends the session at the end of the pulled branch, no keeps it on the branch being worked on, and either way both branches are in the file, so `/tree` reaches the other one. A clean comparison is confirmed rather than hidden (`matches this session's history — no divergence found`); `announceClean: false` suppresses it. Event-driven automation stops short of this on purpose: `switchSession` exists only on the command context, so an idle-time or settled-time handler cannot relocate the live session. Remote JSONL snapshots are cached only under `agent/handoff-cache/`, which must not be tracked. The production helper stores snapshots under `~/.local/state/pi/remote-sessions`; installation or update of that helper is an explicit confirmed operation only, and headless installation is denied. Single-shot synchronization must finish inside the acquired lock lifetime; chunked uploads renew the lease as they progress.

## Transfer cost and safety

Requests to one host share a single multiplexed SSH connection (`ControlMaster=auto`, sockets in `../handoff-cache/sockets/`, falling back to the system temp directory when that path is too long for OpenSSH's socket limit, and dropped entirely when the directory is unwritable). A 5 MB session needs eight protocol requests; without multiplexing each one pays a fresh handshake, which is what made large sessions feel slower after chunking removed the 5 MB ceiling. `multiplex: false` opts out for isolated harnesses. A verified helper is also trusted for `HELPER_READY_TTL_MS` instead of being re-handshaked on every request, and that window ends immediately when a helper is installed or its checksum stops matching.

Two guards keep a fast transfer from being a destructive one. A push may only replace a remote head this session acknowledged (`state.manifest`), or one whose entries the local file already contains. Compare-and-set cannot detect the dangerous case — it reads the expectation moments before committing, so it always matches — so when the remote holds turns this session never read, a push from a command context (`/ssh sync`, move) first merges them in exactly the way `/ssh pull` does: it states the divergence in numbers, asks only where to land (the consent came from running the command), continues the conversation in a merged session file with the unread turns as a sibling branch, and finishes the push from there (`Handoff sync: merged N remote turns in as a branch and pushed the combined session to <alias>`). The idle auto-sync cannot relocate a session, so it reports the conflict instead; merging without relocating would be unsound, because the merged content must become the local file or the next push would delete the imported turns. And a pull whose remote fingerprint still equals the last synchronized one is answered from that fingerprint alone, with no transcript download.

Chunk sizes are measured, not chosen: each chunk aims to occupy the link for about half a second, so a fast network carries large chunks (up to the negotiated helper cap and 4 MiB) and a poor one stays conservative (at least 256 KiB, halved after a failed transfer). Measurements persist per host under `../handoff-cache/chunk-sizes.json` and are advisory only.

`tests/live-handoff.test.ts` is opt-in and never enabled in CI. Before running it, independently verify the server key in an owner-controlled known-hosts file and use a dedicated disposable VM with SSH ingress restricted to the tester. The harness enforces BatchMode, strict supplied known-host verification, no agent forwarding, X11 forwarding, arbitrary forwarding, or local commands. It may use the local SSH agent for authentication, but never forwards that agent to the host. Every run stages its helper and all state beneath a random `$HOME/.local/state/pi/handoff-live/<run-id>` root, validates that boundary before recursive cleanup, and never touches the production helper or state root. It covers helper preflight, malformed protocol input, locking/renewal/contention/recovery, invalid tokens, commit/fetch/CAS, real synchronization, routed file/search/Bash operations, path/injection rejection, timeout/abort, no local fallback, and cleanup.

```sh
PI_HANDOFF_LIVE_TEST=1 \
PI_HANDOFF_LIVE_TARGET=exouser@pi.jetstream-cloud.org \
PI_HANDOFF_LIVE_KNOWN_HOSTS="$HOME/.ssh/known_hosts" \
npx -y tsx --test agent/extensions/02-handoff/tests/live-handoff.test.ts
```

`PI_HANDOFF_LIVE_PORT` and an absolute `PI_HANDOFF_LIVE_IDENTITY_FILE` are optional. Never use `StrictHostKeyChecking=no`, `accept-new`, `/dev/null`, or an unverified `ssh-keyscan` result.
